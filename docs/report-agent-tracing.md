# Report agent tracing

## What is retained

New report runs retain exact system and user/task prompts, response schemas, returned structured model content, usage/model metadata, dispatch order and timestamps in `report_trace_calls`. Calls are associated with both the run and its attempt. Requests are saved before inference, so an interrupted call remains pending rather than disappearing. Reclaimed attempts cannot update their predecessors' records.

`report_trace_events` records run start, the coordinator's review outcome and issue codes, fallback selection and its cause, and final outcome. Full reviewer reasons and manager decisions remain in the corresponding model responses even when a subsequent verified rule fallback is issued. Exact reviewed drafts are retained in task prompts, so reviews can be associated with their actual text rather than a later revision. This does not capture hidden model reasoning or reconstruct exchanges from old runs.

Traces do not change clinical approval, repair, fallback, or PDF behaviour. Failure to persist a trace stops the run with `REPORT_TRACE_UNAVAILABLE` before unlogged inference/publication. Optional highlighting cannot swallow a trace failure and allow publication to continue. Normal model failures still use the existing fallback policy and retain safe error codes; arbitrary upstream exception bodies are not stored.

## Access and retention

Administrators can open **AI usage → View agent trace**. This separately fetches `GET /admin/report-ai/runs/:runId/trace`, protected by the existing enabled-admin cookie session. Deployment credentials cannot access this endpoint. Responses use `Cache-Control: no-store`; displayed content is escaped plain text. Closing the viewer removes its content from component state. Regular usage lists, deployment report responses, console logs and PDFs do not contain the trace.

Messages contain assessment-derived clinical data. Store them in the protected Scoring database under its existing encryption, backup and access controls. Do not copy them into operational logs. Authorization is at the platform administrator level, matching the current administration system; this feature does not add a new clinical-review role.

Retention is **30 days from each call/event's creation**. Expired content is excluded from reads immediately. Startup and hourly cleanup remove up to 1,000 expired rows from each trace table per invocation. Physical cleanup may take further batches for a backlog; database backup lifetimes remain separate. Usage metadata and final reports retain their existing lifetimes. This retention setting is a code constant in `report-trace-store.ts`.

Apply migration `0032_report_agent_traces` before deploying the API. Readiness requires both trace tables. The real runtime uses `PostgresReportTraceStore`; tests/default in-memory applications use an explicitly linked `MemoryReportTraceStore`.

## Report workflow after the review fixes

The manager resolves differing matched energy/protein ranges before drafting, with a source selection or withheld numeric target and a recorded rationale. Deterministic checks prohibit invented target ranges, overriding matched renal restrictions or discarding an applicable matched source because a triggering fact was absent from reduced context. Recorded drug classes and target resolutions travel to every relevant writing/audit stage. Patient-facing target cards use the same selected or withheld decision.

Narrative-only reviews cannot demand future cards. Complete conditional effect cards are generated and audited before assembled coverage. Card context includes relevant matched status/treatment care, but routine numeric target lines are not promoted into additional card-specific obligations. Coverage can repair actual card gaps in the card array; changed cards receive independent re-audit. A new card gap found during a later recheck receives one targeted card repair and another audit, preserving other cards. Mixed source rows can repair both nutrition and treatment fields, placing each action by meaning rather than by the source row type. Source-derived instructions supply clinical requirements. Example food lists are not mandatory exhaustive checklists unless the source says so.

Targeted revisions preserve other fields. Prior source/placement adjudications are supplied to later reviewers to prevent unexplained flip-flops while allowing correction of a genuinely unsafe earlier ruling. Coverage is recalculated after edits, including when the new clinical review rejects the repaired wording. The returned candidate and diagnostic issues always describe the current version.

When a required narrative field remains rejected, the manager may use a verified rule-based replacement for that field only. The assembled candidate receives fresh clinical review and coverage. Unscoped errors or invalid replacements remain held; they do not silently replace all approved prose. Origins and target resolutions are recorded in the private trace. `SECTION_FALLBACK` indicates section recovery, and the admin usage page distinguishes it from whole `RULE_FALLBACK`. A whole rule fallback remains available for failures before an agent draft exists, not normal section rejection.

Highlighting runs only after final clinical acceptance. Each section uses at most one model formatting pass, followed by deterministic span validation. A report-wide budget permits at most 36 clinical calls and 24 optional highlighting calls. A spent clinical budget produces a held report rather than repeating the whole pipeline indefinitely. Explicit HTML-review attempts are not automatically regenerated after clinical rejection.

Regimen quantities, units, preparation, frequency and duration remain in the structured supplement plan. Narrative duplication is rejected so a per-day quantity cannot silently become an administration frequency. Instructions for clinician-managed feeding must identify the clinical team as the actor.
